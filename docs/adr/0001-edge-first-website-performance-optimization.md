# ADR-0001：网站加载优化采用“测量分层、边缘优先”的策略

- 状态：Accepted
- 日期：2026-08-15

## 背景

“网站加载慢”可能来自 DNS/TLS、首字节、静态资源传输、依赖瀑布、超大 API、主线程长任务或缓存失效。若未先区分这些层次，直接升级服务器、接入 CDN 或拆前端包，很容易优化错对象。

本次案例中，入口 TTFB 小于 100 ms，入口 HTML 与主要静态资源的上游响应为毫秒级；另有约 5.4 秒的非关键统计请求，但登录后冷加载需要传输 4.57 MB，LCP 约 30.67 秒。因此首屏的主导瓶颈是公网文本传输和资源复用，而不是入口 HTML 与静态资源的上游计算。

## 决策

采用以下固定顺序：

1. 分别测量 DNS、TCP、TLS、TTFB、总耗时、传输字节、FCP、LCP 和冷/热加载。
2. 当 TTFB 正常而传输慢时，优先在边缘层启用文本压缩。
3. 只对带内容指纹的静态资源设置长期 `immutable` 缓存。
4. 将普通 HTTP 响应与 SSE/WebSocket 路径拆开：普通响应保留代理缓冲，事件流关闭缓冲和 gzip。
5. 对超大 JSON 同时采用压缩和结构治理；压缩不能替代分页、懒加载和字段裁剪。
6. 将非关键请求移出首屏关键路径，并以增量计算降低服务端真实成本。
7. 只有完成压缩和缓存后，才评估 CDN 或公网带宽升级。

## 不变量

- 未指纹化的 URL 不使用一年期 `immutable`。
- 登录后或个性化内容不进入共享缓存；`private` 只限制共享缓存，不能解决同一浏览器切换账号后的隔离问题。长期缓存的字节内容必须与用户身份无关。
- 动态 API 不继承静态资源的长期缓存策略。
- 新 `location` 中一旦定义 `add_header`，就必须按 Nginx 版本重新验证或完整声明父级 HSTS、CSP 等安全响应头。
- SSE 不被缓冲或 gzip；WebSocket 仅在客户端请求 Upgrade 时转发 Upgrade 头。
- source map 的可用性要与线上排障/错误监控需求共同决策，不能为了流量一刀切删除。
- 每次改动必须同时验证冷加载、热加载、API、SSE/WebSocket 和认证边界。

## 未采用的方案

### 先上 CDN

CDN 无法自动解决未压缩响应、错误缓存策略、超大动态 JSON 或串行启动任务。它应是边缘基础优化后的放大器，而不是第一步。

### 全站关闭 `proxy_buffering`

这会让普通响应跟随慢客户端同步传输，使源站连接更久地被占用。只应对明确的流式端点关闭。

### 所有资源统一长期缓存

没有内容指纹的资源更新后 URL 不变，长期缓存会让用户持续拿到旧版本；动态和认证响应还可能引入数据泄漏风险。

### 只做前端代码拆包

本案例的首要瓶颈是 4 MB 以上的未压缩传输。在没有证据表明主线程或单包解析占主导前，拆包不是最高收益动作。

## 结果

包含 gzip 与请求分流的边缘层调整后，冷加载传输量从 4.57 MB 降至 1.14 MB，LCP 从约 30.67 秒降至 3.90 秒；其中，文本资源的离线压缩估算和线上 JSON 压缩前后响应字节对照支持 gzip 是传输量下降的主要来源，但没有为 `proxy_buffering` 做单变量性能对照。内容指纹缓存启用后，热加载只传输约 22.7 KB，LCP 约 0.83 秒。一个 4.25 MB 的 JSON 响应经 gzip 后传输约 369 KB。

这些数字是一组代表性的单次前后对照，不是所有站点的性能承诺；可复用的是测量顺序、缓存边界和验证方法。超大 JSON 的结构治理、非关键请求延迟/增量聚合，以及 CDN/带宽升级仍是后续方案，不计入上述实测改善。
